# Иерархия меню: план и хендофф для новой сессии

Задумано пользователем 2026-11-08, сразу после того, как «разделы» (конструктор) были готовы на ветке `sections`.
Здесь только проект: **кода иерархии ещё нет**. Файл написан, чтобы новая сессия начала с работы, а не с расспросов.
Секретов в файле нет, и не должно быть. Когда иерархия выложена и проверена, файл можно удалить: всё нужное уйдёт в
`docs/decisions.md` («Menu tree»), `docs/deploy.md` и `docs/smoke-checklist.md`.

## 1. Что просит пользователь

Дословно: «сделать иерархию разделов. Типа раздел "Животные приюта" и в него кошек и собак. Архив визитов ставить под
визиты выпадашкой. И так далее, чтобы при создании и редактировании материалов в админке можно было выбирать, на какой
уровень их определить».

Целевое меню из примера:

```
Животные ▾          ← группа: только выпадашка, своей страницы нет
   Кошки            /ru/cats      (как сейчас)
   Собаки           /ru/dogs      (как сейчас)
Гайд                /ru/guide
Визиты ▾            /ru/visits    (у родителя своя страница и свои дети)
   Архив визитов    /ru/archive   (раздел из конструктора)
Как помочь          /ru/help
Статьи              /ru/articles  (раздел из конструктора, верхний уровень)
```

Пять пунктов верхнего уровня, как сейчас, поэтому **шапка снова в одну строку**: двухрядная шапка, которую я ввёл в
ветке `sections`, была вынужденной мерой против длинного плоского меню, и иерархия её снимает (см. п. 5).

### Как я это понял (пользователь подтвердил, п. 11)

«Иерархия» = **дерево меню сайта**: что где лежит в навигации. Это не вложенные адреса и не вложенные рубрики статей.
«Материалы» = всё, что стоит в меню: страницы сайта (Кошки, Собаки, Гайд, Визиты, Как помочь), разделы конструктора и
новые группы. «Выбирать уровень» = в форме раздела (при создании и правке) выпадающий список «Где в меню», а для
страниц сайта и групп отдельная страница админки «Меню сайта».

## 2. Решение в двух словах

| Вопрос | Решение | Почему |
|---|---|---|
| Что такое иерархия | дерево меню, **адреса не меняются** (`/ru/cats` остаётся, архив остаётся `/ru/archive`) | не ломает ссылки, закладки и поиск, не нужны редиректы; без сохранённого дерева и без разделов публичные страницы остаются байт в байт |
| Кошки и собаки | остаются особыми страницами (не разделы конструктора), в дереве стоят как узлы-страницы | у них возраст, стадия, «как забрать», карточки с фильтрами; перенос в конструктор потерял бы это |
| Глубина | **2 уровня** (верхний + выпадашка). Модель хранит любую глубину, ограничение одна константа | на сенсорных экранах и для клавиатуры вложенные всплывающие меню плохи; пользователь сказал «и так далее», поэтому модель не запирает |
| Группа | узел без своей страницы: только название на трёх языках и выпадашка | «Животные приюта» нужен как папка; посадочную страницу при желании делают разделом |
| Родитель со своей страницей | допустим (Визиты и Архив): название-ссылка + отдельная кнопка-шеврон | пример пользователя |
| Скрытие из меню | можно у любого узла, в том числе у страниц сайта: флаг `hidden`; скрывает пункт **и всё его поддерево**, сама страница остаётся доступной по адресу и по ссылкам с других страниц | ответ пользователя на вопрос 5 («наверное, можно»); подробности п. 3, 4 и 6 |
| Где хранить | **один документ `MenuTree`** в новой таблице `site_menu` (одна строка) | дерево правится целиком, перестановка = чистая функция над деревом, одно сохранение |
| Что в дереве по умолчанию | пока документа нет, меню = как сейчас: пять страниц, затем разделы по `position` | сайт без правок не меняется |

## 3. Модель данных

Пакет `model/` (`Menu.kt`), всё `@Serializable`, с умолчаниями (старые документы читаются):

```kotlin
// Идентификатор узла один и несёт вид: "page:cats", "section:3", "group:g2".
@Serializable data class MenuNode(
    val id: String,
    val parent: String? = null,      // id узла-родителя; null = верхний уровень
    val position: Int,               // среди соседей, шаг 10 (10, 20, 30…), чтобы вставка не пересчитывала всех
    val title: LocalizedText? = null,      // только у групп: название на трёх языках
    val menuTitle: LocalizedText? = null,  // только у групп: короткое название для меню (как у раздела)
    val hidden: Boolean = false            // скрыт из меню вместе с поддеревом; страница от этого не исчезает
)

@Serializable data class MenuTree(
    val nodes: List<MenuNode> = emptyList(),
    val nextGroupNumber: Int = 1      // ключи групп g1, g2… не переиспользуются
)
```

- **Страницы сайта** описаны в коде (`SystemPage`: ключ, путь, ключ сообщения для названия, порядок по умолчанию):
  `cats`, `dogs`, `guide`, `visits`, `help` с порядком 10…50, как сейчас. Их нельзя удалить; можно переставлять,
  переносить и **скрывать из меню** (`hidden`). Скрытие убирает только пункт: `/ru/cats` по-прежнему открывается по
  адресу и по ссылкам («Каталог кошек» на главной, «Как помочь» в подвале и на главной), поэтому в админке рядом с
  кнопкой стоит такая подсказка.
- **Разделы** берутся из таблицы `sections`; узел `section:<id>` только говорит, где раздел стоит. Раздел, у которого
  узла нет, стоит на верхнем уровне в конце, порядок (`Section.position`, затем `id`), то есть как сейчас.
- **Группы** живут только в дереве.
- Первое же сохранение из админки **материализует** дерево целиком (все страницы, все разделы, группы), чтобы порядок
  страниц сайта был записан явно. Дальше: узел, чья цель исчезла (удалили раздел), отбрасывается при чтении;
  новый раздел без узла добавляется в конец верхнего уровня.

Новая таблица (как остальные, обычный SQL, который понимают PostgreSQL и H2), в `repository/Database.kt`:

```sql
CREATE TABLE IF NOT EXISTS site_menu (
    id INTEGER PRIMARY KEY,
    data TEXT NOT NULL,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL
)
```

Репозиторий: `MenuRepository { fun load(): MenuTree? }` и `MutableMenuRepository { fun save(tree: MenuTree) }`;
`NoMenu`, `InMemoryMenuRepository` (файлы без базы и тесты), `PgMenuRepository` (одна строка с `id = 1`, запись «сначала
UPDATE, если строки нет, INSERT» как у `upsertPhoto`, кэш 30 с и сброс при записи как у `PgDocuments`). Копия (zip):
`menu.json` рядом с `sections.json`; сидер читает его из `data/` на пустой базе; без базы сайт читает `data/menu.json`
только для чтения. README в копии и тесты копии обновить (в ветке `sections` они уже знают про `sections.json`).

## 4. Как строится меню

Новый сервис `service/MenuService.kt` заменяет `SectionService.menu()`: вход (дерево или `null`, разделы, записи,
язык), выход дерево пунктов для показа.

```kotlin
class NavItem(
    val id: String,
    val label: String,          // у страницы сайта пусто: подпись берёт вид из сообщений (см. ниже)
    val href: String?,          // null: у группы нет страницы, у раздела нет страницы на этом языке
    val children: List<NavItem>
)
```

Алгоритм (чистая функция, это главное, что покрыть тестами):

1. Узлы = сохранённые узлы, чья цель существует, плюс узлы по умолчанию для целей без узла.
2. Родитель, которого нет (удалён, не прошёл проверку), заменяется верхним уровнем. Цикл или глубина больше предела:
   узел поднимается на верхний уровень (данные из копии могут быть любыми, читать надо защищённо).
3. Сортировка соседей по `position`, затем по `id`.
4. **Скрытые узлы:** узел с `hidden = true` и всё его поддерево в меню не попадают (дети скрытого родителя не
   «всплывают» на уровень выше: скрытие читается как «закрыть ящик целиком»). Дальше работают только оставшиеся узлы.
5. **Видимость на языке:**
   - страница сайта видна всегда (если не скрыта вручную);
   - раздел виден, если у него есть опубликованная запись с названием на этом языке (как сейчас, `SectionService`);
   - группа видна, если виден хотя бы один её ребёнок;
   - родитель с видимым ребёнком виден всегда. Если у родителя-раздела на этом языке нет своей страницы
     (`href == null`), он превращается в «только выпадашку».
6. Подпись: страница сайта берёт название из сообщений (`nav.cats`, `nav.guide.short`, …), раздел
   `menuTitle` иначе `title` (`Section.menuLabel`), группа `menuTitle` иначе `title` (`forLocale`).

Служба отдаёт только структуру. Подписи страниц сайта на трёх языках подставляет вид (у него есть `ResourceBundle`
из `messagesFor(locale)`), сама служба `ResourceBundle` не знает.

## 5. Публичная часть

**Передача в вёрстку.** `views/SiteMenu.kt` сейчас несёт плоский `List<MenuEntry>` только для разделов, а пять
фиксированных ссылок прописаны прямо в `navigation()` (`views/NavigationViews.kt`). Теперь `SiteMenu` несёт **всё
меню** (`List<NavItem>`), а `navigation()` его рисует. Если меню не задано (виды, которые вызывают без `respondPage`,
например в тестах видов), `navigation()` рисует пять фиксированных ссылок как раньше. Ключ в атрибутах приложения
`SectionMenuKey` переименовать в `SiteMenuKey`, он указывает на `MenuService::build`.

**Гарантия:** без сохранённого дерева и без разделов шапка совпадает с нынешней байт в байт (существующие тесты и
сравнение 25 публичных страниц до и после выкладки это проверят).

**Разметка** узла с детьми (в `<nav class="main-nav">`):

```html
<div class="nav-group">
  <a href="/ru/visits">Визиты</a>                      <!-- у группы без страницы: <span class="nav-label"> -->
  <button type="button" class="nav-toggle" hidden aria-expanded="false" aria-controls="nav-sub-visits"
          aria-label="Подразделы: Визиты"></button>
  <div class="nav-sub" id="nav-sub-visits"><a href="/ru/archive">Архив визитов</a></div>
</div>
```

- **Без JavaScript:** на настольной ширине подменю открывается по `:hover` и `:focus-within` (мышь и клавиатура
  работают без скрипта); кнопка-шеврон спрятана (`hidden`), как кнопка «Показать пароль»; на телефоне (≤760 px)
  подменю всегда показано под родителем, с отступом. Принятый риск: сенсорный планшет шире 760 px с выключенным
  JS не откроет подменю (родитель-страница всё равно ведёт на свою страницу).
- **С JavaScript** (`static/scripts/nav-menu.js`, `defer`, по образцу `cat-gallery.js`): скрипт показывает кнопки,
  переключает `aria-expanded`, закрывает по Esc (фокус возвращается на кнопку), по клику вне меню и когда фокус ушёл.
- **Текущая страница:** `aria-current="page"` только на ссылке самой страницы (сейчас `navLink`, `matchChildren`);
  родителю, у которого открыта дочерняя страница, ставят класс (подчёркивание), не `aria-current`.
- Касания: кнопка и ссылки 44 px по высоте, как остальные органы шапки.
- Вид выпадашки по вкусу пользователя (скриншоты, не вслепую): плоская, плотная, зелёный и нейтральный серый, без
  теней: фон `--color-bg`, рамка 1 px `--color-line`, радиус 4, нет оранжевого и беж.
- **Правило одной и двух строк.** Класс `has-sections` на `<header>` (двухрядная шапка из ветки `sections`, CSS в
  `main.css` под `@media (min-width: 761px)`) заменяется правилом по числу пунктов **верхнего уровня**: до 5 одна строка
  (как сегодня), 6 и больше две. Замеры из сессии разделов: шесть пунктов в ru и en уже не влезают в строку ниже ~900 px,
  пять влезают. Шеврон добавляет ширину, пересмотреть замер на сербском («Kako pomoći» самое длинное) и на 800 и
  1100 px. Константа `MAX_ONE_ROW_ITEMS = 5` в одном месте; класс переименовать (например `nav-two-rows`) и обновить
  два теста в `SectionRoutesTest` (они ищут `has-sections`).

## 6. Админка

**1) Новая страница «Меню сайта»** (`/admin/menu`, пункт в `AdminSection`, четвёртый в шапке админки; на телефоне
шапка админки уже переносится). Дерево списком с отступом, у каждого узла строка:

```
Животные приюта        [группа]    ↑ выше  ↓ ниже   Перенести в: [Верхний уровень ▾] [Перенести]   Переименовать · Удалить
   Кошки               [страница]  ↑ ↓              Перенести в: […]
   Собаки              [страница]  ↑ ↓              Перенести в: […]
Гайд                   [страница]  ↑ ↓              Перенести в: […]
Визиты                 [страница]  ↑ ↓              Перенести в: […]
   Архив визитов       [раздел]    ↑ ↓              Перенести в: […]   · не виден: нет опубликованных записей
```

Всё на формах и POST без JS, с токеном (`withForm`), как остальная админка. Действия:

- `POST /admin/menu/move` (`node`, `direction=up|down`): обмен с соседом, перенумерация шагом 10.
- `POST /admin/menu/parent` (`node`, `parent`): перенос в конец списка детей нового родителя.
- `POST /admin/menu/visibility` (`node`, `hidden=true|false`): «Скрыть из меню» / «Показать в меню». Строка скрытого
  узла помечена, у родителя написано, что дети скрыты вместе с ним; рядом подсказка, что страница остаётся доступной по
  адресу и по ссылкам с других страниц. Для узла с видимыми детьми кнопка предупреждает, сколько пунктов уйдёт вместе с ним.
- `POST /admin/menu/groups` (название на трёх языках, короткое название): новая группа в конец верхнего уровня.
- `GET/POST /admin/menu/groups/{key}`: переименование. `GET/POST /admin/menu/groups/{key}/delete`: подтверждение;
  дети группы переходят на уровень удаляемой, в конец, порядок сохраняется.
- Список «Перенести в» содержит «Верхний уровень» и только допустимых родителей: верхнего уровня, не сам узел, и
  не тот, чьё вложение превысило бы глубину (узел с детьми можно только на верхний уровень).
- Серверная проверка повторяет всё это (форму можно подделать); ошибка возвращает страницу с набранным.
- Узлы, которые посетитель сейчас не увидит, помечены с причиной (скрыт вручную, раздел без опубликованных записей,
  группа без видимых детей). Полезно и показать «Как увидит посетитель» по языкам плоским текстом.

**2) Выбор уровня в форме раздела** (требование пользователя «при создании и редактировании»). В
`admin/AdminSectionViews.kt` поле «Место в меню» (число 0–99, `position`) заменяется выпадающим списком **«Где в
меню»**: «Верхний уровень» и допустимые родители. Новый раздел встаёт в конец выбранного уровня. Смена родителя при правке
переносит узел в конец нового родителя; порядок среди соседей правится на странице «Меню сайта». Код: `SectionForm`
(`SectionForms.kt`: `position`, `MAX_POSITION`, `newValues`), `AdminSectionRoutes.kt` (создание, настройки), а после
сохранения раздела вызывается `MenuTree`-операция «поставить узел». Заготовка «Архив визитов» может предлагать
родителем «Визиты» по умолчанию.
Для форм раздела нужен только выбор родителя; для страниц сайта и групп он живёт на странице «Меню сайта».

**3) Список разделов** (`/admin/sections`): в строке раздела писать, где он стоит («Визиты › Архив визитов»).

`Section.position` остаётся в модели как порядок по умолчанию, пока дерево не сохранено; из формы поле уходит.
Ограничение `MAX_SECTIONS = 6` пересмотреть: оно было из-за ширины меню, с выпадашками меню вмещает больше (например 12).

## 7. Что осознанно не делаем и почему

- **Не вкладываем адреса** (`/ru/animals/cats`). Это сломало бы ссылки и поиск и потребовало бы редиректов и правок
  `hreflang`, а пользователь просил про меню («выпадашкой»). Если захочется, это отдельный этап.
- **Не переносим кошек и собак в конструктор.** Потеряли бы их особые поля и страницы.
- **Не делаем вложенность глубже двух уровней в интерфейсе** (всплывающие меню второго порядка).
- **Не делаем иерархию записей внутри раздела** (рубрики статей). Для этого уже есть метки. Если пользователь имел в
  виду именно это, это другая задача (п. 11, вопрос 1).
- **Не ведём подвал меню по дереву.** Подвал не менялся и в этот этап не входит.
- **Хлебные крошки** («Визиты › Архив визитов») не входят; ссылка «← раздел» на странице записи остаётся. Можно добавить
  позже по тому же дереву.

## 8. Крайние случаи (каждый превратить в тест)

- Узел ссылается на удалённый раздел или несуществующую страницу: отбрасывается молча.
- Родитель отсутствует, цикл, глубина больше предела (например, из копии): узел поднимается на верхний уровень.
- Раздел-родитель без страницы на этом языке, но с видимым ребёнком: пункт без ссылки (только выпадашка).
- Группа с одним ребёнком, невидимым на этом языке: группа не видна на этом языке.
- Скрыта страница сайта, на которую ведёт ссылка с главной или из подвала: ссылка работает, пропадает только пункт меню.
- Скрыт родитель с видимыми детьми: дети скрыты вместе с ним. Скрыт ребёнок: остальные остаются. Скрыты все дети
  группы: группа тоже не показывается.
- Все пункты верхнего уровня скрыты: меню пустое (`<nav>` без ссылок), страница не падает.
- Число пунктов верхнего уровня для правила «одна или две строки» считается по **видимым** на этом языке.
- Удаление раздела, у которого есть дети в дереве: дети остаются, поднимаются на его место (конец его уровня).
- Удаление группы: дети на уровень удалённой, порядок сохранён.
- Перенос узла с детьми под другой узел: отказ (глубина).
- Два одинаковых id в документе: учитывается первый.
- Название группы пустое на языке: берётся по порядку `forLocale` (en, ru, sr), как у остальных текстов; русское обязательно.
- Ошибка чтения дерева из базы (база спит): меню по умолчанию, не пустая страница (как сегодня с разделами).
- Страница сайта нигде не записана в дереве (старый документ): добавляется по умолчанию.
- Сайт без базы: читает `data/menu.json` (если есть), только чтение.

## 11. Решения пользователя (2026-11-08, после этого плана)

Вопросы заданы, ответы получены, **спрашивать заново не нужно**:

1. Иерархия — это дерево меню, адреса не меняются, рубрик внутри раздела статей нет (для них метки). **Да.**
2. Два уровня: верхний и выпадашка. **Да.**
3. «Животные приюта» — группа без своей страницы, только выпадашка. **Да.**
4. Кошки и собаки остаются особыми страницами и переезжают в дерево. **Да.**
5. Страницы сайта (например «Гайд») можно скрывать из меню. **«Наверное, можно»**: сделано флагом `hidden` на узле
   (п. 3, 4, 6, 8); пользователю в конце сессии показать, как это выглядит, и убедиться, что устраивает.
6. `sections` выкладывается **отдельным первым релизом**, иерархия вторым (п. 10, этап 0). **Да.**
7. Короткое название для меню у группы, как у раздела. **Не отвечено**, по умолчанию: да (оно уже в модели).

Если по ходу работы выяснится, что что-то из этого не так (например, для телефона два уровня тесны), остановиться и
спросить, а не решать за пользователя.
