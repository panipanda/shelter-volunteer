# ИИ в тестировании

Тестирование — одна из самых естественных областей для работы с агентом: у задач есть чёткий критерий (тест падает или проходит), у результата есть проверка (запуск), а объём рутины огромен. Но есть и коварная особенность: агент отлично пишет **правдоподобные** тесты, которые проверяют не то, что нужно. Тест, который всегда зелёный, хуже отсутствия теста, потому что создаёт ложное чувство безопасности. Поэтому в этом уроке главный навык не «как заставить ИИ написать тесты», а «как понять, чего стоят тесты, написанные ИИ».

После урока вы сможете:

- применять ИИ на этапах тест-дизайна, автоматизации, исследовательского тестирования и разбора ошибок;
- формулировать запросы, не дающие агенту «подогнать тест под код»;
- проверять качество тестов мутациями и свойствами;
- написать скрипт исследовательской проверки с браузером и понимать, что машине судить нельзя.

## Где ИИ помогает тестировщику

| Этап | Что делает агент | Главный риск |
|---|---|---|
| Анализ требований | ищет противоречия, пропущенные случаи, неоднозначности | выдумывает «требования», которых нет |
| Тест-дизайн | предлагает классы эквивалентности, границы, таблицы решений | не знает вашего продукта и пропускает его особенности |
| Тестовые данные | генерирует разнообразные и «злые» входы | нереалистичные или повторяющиеся данные |
| Автотесты | пишет код тестов по описанию | тавтологичные тесты, повторяющие реализацию |
| Исследовательское тестирование | ходит по сайту через браузер и сообщает наблюдения | пропускает то, что «выглядит неправильно» для человека |
| Разбор падений и нестабильности | читает логи, находит закономерности | уверенное, но неверное объяснение причины |
| Отчёты об ошибках | оформляет шаги, ожидаемое и фактическое | неточные шаги воспроизведения |
| Оценка релиза | собирает сводку по тестам и рискам | вывод без проверки данных |

Общая рамка: ИИ **ускоряет черновик**, человек отвечает за **суждение**. Особенно там, где машина сама не может узнать, что «правильно».

## Тест-дизайн: давайте требование, а не код

Главное правило. Если показать агенту реализацию и попросить «напиши тесты», он выведет ожидания **из кода**, и ошибки реализации превратятся в «ожидаемое поведение». Если показать **требование** («возраст считается с той точностью, какая известна: без месяца в годах, с месяцем в месяцах до достижения года»), он выведет ожидания из него, и тест найдёт расхождения.

```text
Плохо:   Вот функция displayCatAge, напиши на неё тесты.

Хорошо:  Требование: возраст кошки считается с той точностью, какая известна.
         Без месяца: в годах ("Младше года", "1 год", "N лет").
         С месяцем: в месяцах, пока не исполнился год.
         Неизвестный год: "Возраст неизвестен".
         Построй таблицу тест-кейсов: классы эквивалентности, граничные значения, нестандартные входы
         (будущая дата, месяц без года). Для каждого укажи ожидаемый результат ИЗ ТРЕБОВАНИЯ.
         Код функции пока не открывай. Если ожидаемое неясно из требования, задай вопрос.
```

Хороший агент вернёт в том числе вопросы вроде «что показывать при рождении в текущем месяце?»: именно в такой неоднозначности мы нашли дефект «0 месяцев» в уроке про [алгоритмы](lesson:a2-algorithms) (в проекте он уже исправлен). Требования с дырами — самый ценный результат тест-дизайна, и ИИ хорош в том, чтобы их находить.

Техники, которые стоит назвать агенту по именам:

| Техника | Идея | Пример для сайта |
|---|---|---|
| Классы эквивалентности | входы делят на группы с одинаковым поведением | год: неизвестен / в прошлом / в этом году / в будущем |
| Граничные значения | ошибки живут на краях | 11, 12, 13 месяцев; ровно в момент отправления |
| Таблица решений | сочетания условий | опубликована × есть перевод × язык страницы |
| Переходы состояний | допустимые переходы | черновик → опубликована → снова черновик |
| Попарное сочетание | не все сочетания, а все пары | язык × тема × ширина экрана |

## Тесты, написанные агентом: проверка качества

Типичные дефекты тестов агента и защита:

| Дефект | Пример | Как поймать |
|---|---|---|
| **Тавтология** | ожидаемое значение вычислено той же формулой, что и в коде | ожидаемое всегда записано как константа |
| **Слабая проверка** | `assertNotNull(result)`, `assertTrue(list.isNotEmpty())` | спросить: «что ещё должно быть верным?» |
| **Проверка реализации** | мок проверяет порядок вызовов | проверять результат (см. [тестирование](lesson:a3-testing)) |
| **Один счастливый путь** | нет границ и ошибок | таблица случаев в запросе |
| **Нестабильность** | `sleep`, текущая дата, общий state | время и данные подменяются; прогон 20 раз |
| **Тихое ослабление** | чтобы позеленело, агент поправил проверку | читать дифф тестов отдельно |

### Мутации: самая честная проверка

Вопрос «хороши ли тесты» имеет проверяемый ответ: **испортите код и посмотрите, упадут ли тесты**. Если после правки `<=` на `<` тесты остались зелёными, они эту границу не проверяют. Это и есть мутационное тестирование. Моделируем его: у нас функция `shortened`, три «мутации» (по одной порче кода) и два набора тестов: слабый (в духе «один счастливый путь») и хороший.

```run
typealias Shorten = (String, Int) -> String

val original: Shorten = { text, limit ->
    if (text.length <= limit) text
    else {
        val cut = text.take(limit)
        cut.substringBeforeLast(' ', cut).trimEnd(',', ';', ':', '-', ' ') + "…"
    }
}

val mutants: Map<String, Shorten> = mapOf(
    "boundary: <= became <" to { text: String, limit: Int ->
        if (text.length < limit) text
        else {
            val cut = text.take(limit)
            cut.substringBeforeLast(' ', cut).trimEnd(',', ';', ':', '-', ' ') + "…"
        }
    },
    "trimEnd removed" to { text: String, limit: Int ->
        if (text.length <= limit) text
        else {
            val cut = text.take(limit)
            cut.substringBeforeLast(' ', cut) + "…"
        }
    },
    "word cut removed" to { text: String, limit: Int ->
        if (text.length <= limit) text else text.take(limit).trimEnd(',', ';', ':', '-', ' ') + "…"
    }
)

class Check(val name: String, val passes: (Shorten) -> Boolean)

val weak = listOf(
    Check("short text is unchanged") { it("Short", 50) == "Short" }
)

val good = weak + listOf(
    Check("exactly at the limit") { it("12345", 5) == "12345" },
    Check("cut at a word") { it("Cats like to sleep in the sun", 15) == "Cats like to…" },
    Check("trailing punctuation removed") { it("one two, three", 9) == "one two…" }
)

fun report(title: String, suite: List<Check>) {
    check(suite.all { it.passes(original) }) { "the suite must pass on the original code" }
    println(title)
    mutants.forEach { (name, mutant) ->
        val killed = suite.any { !it.passes(mutant) }
        println("  ${if (killed) "killed" else "survived"}: $name")
    }
}

fun main() {
    report("weak suite", weak)
    report("good suite", good)
}
```

```output
weak suite
  survived: boundary: <= became <
  survived: trimEnd removed
  survived: word cut removed
good suite
  killed: boundary: <= became <
  killed: trimEnd removed
  killed: word cut removed
```

Слабый набор проходит на оригинале и на **всех** трёх испорченных вариантах: он не защищает ни границу, ни очистку знаков, ни обрезку по слову. Хороший набор убивает все мутации. Покрытие строк у обоих наборов одинаково высокое, ведь одна проверка выполняет весь код ветки. Вот почему «покрытие 90%» ничего не говорит о качестве тестов. В реальном проекте мутации применяют инструменты (для JVM, например, PIT), а для проверки конкретных тестов агента достаточно сделать две-три порчи руками.

### Свойства и «злые» данные

Агент особенно полезен в придумывании входов, которые вы бы не придумали: пустая строка, пробелы, апостроф, кавычки, `<script>`, очень длинное имя, символы разных алфавитов, эмодзи, перенос строки. Из них удобно делать **проверки свойств**: утверждение, которое должно выполняться для любого входа, и случайная генерация.

Свойства функции `petSlug` (адрес страницы из имени): результат состоит только из строчных латинских букв, цифр и одиночных дефисов; не начинается и не кончается дефисом; не пустой; повторное применение не меняет результат.

```test
import kotlin.random.Random
import kotlin.test.Test
import kotlin.test.assertEquals
import kotlin.test.assertTrue

fun petSlug(name: String?, id: Int): String {
    val slug = name.orEmpty()
        .lowercase()
        .replace(Regex("[^a-z0-9]+"), "-")
        .trim('-')
    return slug.ifBlank { id.toString() }
}

class SlugPropertyTest {
    private val alphabet = "abcXYZ019 -_'\"!?.,/\\<>&é Феликс😀\t\n".toList()
    private val safe = Regex("[a-z0-9]+(-[a-z0-9]+)*")

    @Test
    fun `for any name the slug is a safe address`() {
        val random = Random(42)
        repeat(2_000) {
            val name = String(CharArray(random.nextInt(0, 25)) { alphabet.random(random) })
            val slug = petSlug(name, id = 7)

            assertTrue(safe.matches(slug), "the slug of \"$name\" is \"$slug\"")
        }
    }

    @Test
    fun `applying the function to its own result changes nothing`() {
        val random = Random(7)
        repeat(2_000) {
            val name = String(CharArray(random.nextInt(0, 25)) { alphabet.random(random) })
            val slug = petSlug(name, id = 7)

            assertEquals(slug, petSlug(slug, id = 7), "name \"$name\"")
        }
    }

    @Test
    fun `a name with no latin letters falls back to the id`() {
        assertEquals("7", petSlug("Феликс", 7))
        assertEquals("7", petSlug("   ", 7))
        assertEquals("7", petSlug(null, 7))
    }
}
```

Два замечания. Генератор использует **фиксированное зерно** (`Random(42)`): тест остаётся детерминированным, и упавший случай можно воспроизвести. А набор символов — то, что вы просите у агента: «придумай алфавит злых символов для имени кошки». Тест на свойства нашёл бы и дефект с переполнением из урока про [безопасность](lesson:w6-security), и любое имя, ломающее адрес.

## Исследовательское тестирование с браузером

Агент с браузером (Playwright через MCP или обычный скрипт) может **ходить по сайту** и проверять то, что трудно записать в юнит-тест: что страница открывается, есть ли горизонтальная прокрутка на телефоне, не пропали ли картинки. В проекте этим пользовались для скриншотов на ширине 375 пикселей в обеих темах. Вот пример скрипта, который агент напишет за минуту:

```javascript
// Checks pages for horizontal scrolling at phone and tablet width.
import { chromium } from "playwright";

const widths = [375, 768];
const pages = process.argv.slice(2);
const browser = await chromium.launch();

for (const width of widths) {
    const page = await browser.newPage({ viewport: { width, height: 800 } });
    for (const url of pages) {
        await page.goto(url);
        const overflow = await page.evaluate(() => document.documentElement.scrollWidth - window.innerWidth);
        console.log(`${overflow > 0 ? "FAIL" : "ok  "} ${width}px ${url} (overflow ${overflow}px)`);
    }
}
await browser.close();
```

Проверка простая и объективная: если ширина содержимого больше ширины окна, на телефоне появится горизонтальная прокрутка. Подобные проверки «одно условие, один вывод» агент пишет хорошо. Автоматическую проверку доступности добавляют библиотекой axe: `new AxeBuilder({ page }).analyze()` возвращает список нарушений (контраст, пустые кнопки, нет `alt`). Но помните цифру из урока про [доступность](lesson:u2-a11y-perf): машина находит примерно треть проблем.

**Чего агент не заменит.** Он не скажет, что вёрстка «выглядит тесно», что текст кнопки пугает, что порядок блоков неудобен. Скриншоты стоит **смотреть самому**; агент может приложить их как доказательство, но суждение о качестве за человеком. Хорошая практика исследовательской сессии: человек формулирует **хартию** («за 30 минут исследовать страницу кошки на трёх языках и в обеих темах, ища проблемы с длинными именами и отсутствующими фото»), агент проходит рутинные части и пишет наблюдения со ссылками на скриншоты, а человек проверяет и решает, что считать дефектом.

## Скиллы для QA

В репозитории `qa-toolkit` рядом с проектом собран набор скиллов для тестировщиков (подробнее в уроке про [скиллы](lesson:ai2-skills)): универсальный **`qa-copilot`** (анализ требований, тест-дизайн, отладка, расследование нестабильных тестов, оценка релиза; описание подчёркивает: отделять факты от гипотез, проверять возможности среды, опираться на доказательства), а также шаблонные скиллы для написания тест-кейсов, создания задач и подготовки релиза с подстановкой параметров своего проекта. Идея набора: **процессные знания общие, а детали продукта подставляются**. Такой набор превращает «как мы тестируем» в повторяемую процедуру, которую можно улучшать.

## Чек-лист ревью тестов, написанных ИИ

1. Ожидаемые значения выведены из **требования**, а не из кода? Записаны константами?
2. Что проверяется: результат или то, как он получен?
3. Есть ли границы, пустые и ошибочные входы, или только счастливый путь?
4. Если сломать код (мутация), упадёт ли тест? Попробуйте две порчи.
5. Тест детерминирован? Время, случайность, порядок, общее состояние?
6. Название — предложение, говорящее о поведении?
7. Не ослаблена ли какая-то прежняя проверка в этом диффе?
8. Нет ли секретов и реальных персональных данных в тестовых данных?

## Live coding: тест-дизайн с агентом

::::live Требование → таблица → тесты → мутации
Работаем с функцией `shortened` (обрезка длинного текста на карточке).

:::step Шаг 1. Требование без кода
Человек пишет требование и просит таблицу случаев, не показывая код.

```text
Требование: длинный текст на карточке обрезается по границе слова до лимита знаков.
Текст не длиннее лимита остаётся как есть. В конце обрезанного текста нет запятых,
точек с запятой, двоеточий, дефисов и пробелов; добавляется "…".
Составь таблицу тест-кейсов: границы (длина лимит-1, лимит, лимит+1), слово длиннее лимита,
знаки на конце, пустая строка.
```
:::

:::step Шаг 2. Агент задаёт вопросы
Хороший ответ включает вопросы: «что делать, если после обрезки ничего не осталось?», «считать ли длину в символах или в кодовых точках (эмодзи)?», «лимит 0?». Каждый вопрос это **дыра в требовании**, которую нужно закрыть решением, а не молчаливо реализовать.
:::

:::step Шаг 3. Тесты по таблице, затем сравнение с кодом
Теперь агенту показывают код, и он прогоняет таблицу. Расхождения это либо ошибки кода, либо ошибки в таблице: разбираются парами «ожидаемое из требования / фактическое».
:::

:::step Шаг 4. Проверка мутациями
Человек просит: «сломай код тремя способами и покажи, какие тесты упали». Выживший мутант означает недостающий тест. Результат модели выше: слабый набор не убил ни одного.
:::

:::step Шаг 5. Свойства и злые данные
Последний слой: свойства («результат не длиннее лимита плюс одно многоточие»; «повтор не меняет результат») и генератор странных входов. Запустите тест на свойства `petSlug` выше и добавьте такой же к `shortened`: сначала подумайте, какое свойство верно для любого входа и лимита.
:::

## Практика

::::task Найдите слабые места в тестах агента
Агент написал такие тесты для `CatService`. Назовите не меньше пяти проблем и предложите исправления.

```kotlin
@Test
fun testAvailable() {
    val repo = mock<CatRepository>()
    whenever(repo.findAll()).thenReturn(listOf(Cat(1, "A", AdoptionStage.FOR_ADOPTION)))
    val result = CatService(repo).getAvailableCats()
    assertNotNull(result)
    verify(repo).findAll()
}

@Test
fun testSlug() {
    val cat = Cat(1, "Felix")
    assertEquals(cat.name.lowercase(), CatService(repo).getCatBySlug("felix")?.name?.lowercase())
}
```

:::solution
1. **Имена** `testAvailable`, `testSlug` ничего не говорят. Нужны предложения: «черновики не попадают в список доступных».
2. **`assertNotNull(result)`** слабая проверка: пройдёт и для пустого списка, и для неверного. Нужно проверить **содержимое**: `assertEquals(listOf("A"), result.map { it.name })`.
3. **`verify(repo).findAll()`** проверяет реализацию (вызов), а не поведение. Убрать; использовать фейк.
4. **Нет случаев**, ради которых существует метод: черновик, другая стадия, пустой список. Нужны минимум три теста.
5. **Тавтология во втором тесте:** ожидаемое получено тем же `lowercase()`, что и фактическое; тест пройдёт, даже если сервис вернёт не ту кошку. Ожидаемое должно быть константой: `assertEquals(1, service.getCatBySlug("felix")?.id)`.
6. **Переменная `repo` не определена во втором тесте** (в первом она локальная): тест не скомпилируется. Показывает, что агентом присланное нужно запускать.
7. **Нет случая «неизвестный адрес → null» и «черновик недоступен по адресу».**
:::

Напишите запрос агенту для создания тест-кейсов к функции «следующий выезд» (`nextScheduledVisit`), чтобы он **не видел реализацию**. Опишите требование (расписание, отмены, дополнительные, граница отправления) и формат ответа.

:::solution
```text
Требование (без кода). Выезды по расписанию: среда 9:00 и суббота 10:00 (время Белграда).
Функция получает текущее время и необязательные переопределения: отменённые даты и
дополнительные выезды. Возвращает ближайший выезд, который ещё не уехал (в момент
отправления он уже считается уехавшим). Перенос выезда = отмена + дополнительный.
Нужно: таблица тест-кейсов (дано: время, отмены, дополнительные; ожидаемое: дата и время).
Покрой: обычные дни недели, момент отправления и минуту после, выезд сегодня,
подряд идущие отмены, дополнительный выезд раньше и позже регулярных, дополнительный в прошлом,
переход через границу месяца и года, високосный день.
Ожидаемое выводи из требования. Если что-то неясно (например, как считать часовой пояс при смене
времени), задай вопрос, а не угадывай. Код функции не читай, пока не закончишь таблицу.
Формат: markdown-таблица; затем отдельно список вопросов к требованию.
```

Обратите внимание на три приёма: **требование отдельно от кода**; **список областей** для покрытия; **вопросы разрешены** (иначе агент выдумает ответы).
:::

::::task Хартия исследовательского тестирования
Напишите хартию на 30 минут для исследования страницы кошки: цель, области внимания, что делает агент, что делает человек, как фиксировать находки.

:::solution
Пример:

- **Цель.** Найти проблемы отображения и доступности страницы кошки на трёх языках и в обеих темах.
- **Области.** Длинные имена и описания (русский и сербский длиннее английского); кошка без фото и с одним фото; галерея и Esc; кнопка «Написать в Telegram» есть/нет; статус; ширины 375 и 1280.
- **Агент.** Открывает набор страниц (кошки с разными данными), снимает скриншоты по матрице язык × тема × ширина, проверяет горизонтальную прокрутку, сломанные изображения, ошибки в консоли, запускает axe. Приводит таблицу «страница, проверка, результат, ссылка на скриншот».
- **Человек.** Смотрит скриншоты на предмет «тесно», «обрезано», «непонятно»; проходит страницу с клавиатуры; оценивает серьёзность находок.
- **Фиксация.** Каждая находка: шаги, ожидаемое, фактическое, скриншот, версия сайта. Спорные отмечаются как «вопрос к дизайну», а не «ошибка».
:::

## Итоги

- ИИ ускоряет черновики тест-дизайна, данных, автотестов и разведки, а суждение остаётся за человеком.
- Тесты выводите из требований, а не из кода; просите вопросы по неясному.
- Качество тестов проверяйте мутациями и свойствами; чек-лист ревью обязателен.
- Браузерный агент хорош для объективных проверок (прокрутка, ошибки, доступность); вид и удобство смотрит человек.
- Автоматизируйте найденную проблему: каждая ошибка заканчивается новым тестом или правилом.
