# Данные: JSON, SQL и JDBC

Данные живут дольше кода. Код можно переписать за вечер, а записи, которые волонтёры вносили полгода, переписать нельзя. Поэтому решения о формате хранения и о том, как этот формат меняется, одни из самых важных. В этом уроке разберём, как проект хранит кошек и собак, и почему именно так.

После урока вы сможете:

- сериализовать модели в JSON и безопасно развивать их, не ломая сохранённые записи;
- объяснить, чем «документ в таблице» отличается от нормализованной схемы и когда он уместен;
- писать безопасные SQL-запросы через JDBC с транзакциями и пулом соединений;
- построить кэш с ограничением времени жизни, сбросом при записи и ответом из старой копии при отказе базы.

## kotlinx.serialization

Класс помечается `@Serializable`, и компилятор сам генерирует код чтения и записи JSON: без рефлексии и без отдельного описания схемы.

```run
import kotlinx.serialization.Serializable
import kotlinx.serialization.encodeToString
import kotlinx.serialization.decodeFromString
import kotlinx.serialization.json.Json

@Serializable
data class Dog(val id: Int, val name: String, val published: Boolean = true, val age: String? = null)

fun main() {
    val lenient = Json { ignoreUnknownKeys = true }
    val old = """{"id":1,"name":"Sava","removedField":"x"}"""
    println(lenient.decodeFromString<Dog>(old))

    println(Json.encodeToString(Dog(2, "Rex")))
    println(Json { encodeDefaults = true }.encodeToString(Dog(2, "Rex")))
}
```

```output
Dog(id=1, name=Sava, published=true, age=null)
{"id":2,"name":"Rex"}
{"id":2,"name":"Rex","published":true,"age":null}
```

Три наблюдения:

1. В старой записи нет полей `published` и `age`, но она прочиталась: подставились **значения по умолчанию** из класса.
2. Лишнее поле `removedField` игнорируется благодаря `ignoreUnknownKeys = true`. Без этой настройки чтение упало бы.
3. По умолчанию значения, равные умолчанию, **не записываются** (вторая строка). С `encodeDefaults = true` записываются все поля (третья строка). Этот пункт кажется мелочью, но из него вырос важный проектный выбор.

### Почему encodeDefaults = true

Посмотрите на комментарий в [PgRepositories.kt](repo:src/main/kotlin/org/proanima/shelter/repository/PgRepositories.kt):

```kotlin
// Defaults are written out too, so that changing a default in the code later does not silently change
// the pets that were saved before.
internal val documentJson = Json {
    ignoreUnknownKeys = true
    encodeDefaults = true
}
```

Продемонстрируем, от чего это защищает.

```run
import kotlinx.serialization.Serializable
import kotlinx.serialization.encodeToString
import kotlinx.serialization.decodeFromString
import kotlinx.serialization.json.Json

@Serializable
data class DogBefore(val name: String, val published: Boolean = true)

@Serializable
data class DogAfter(val name: String, val published: Boolean = false)

fun main() {
    val stored = Json.encodeToString(DogBefore("Sava"))
    println(stored)
    println(Json.decodeFromString<DogAfter>(stored))

    val storedWithDefaults = Json { encodeDefaults = true }.encodeToString(DogBefore("Sava"))
    println(storedWithDefaults)
    println(Json.decodeFromString<DogAfter>(storedWithDefaults))
}
```

```output
{"name":"Sava"}
DogAfter(name=Sava, published=false)
{"name":"Sava","published":true}
DogAfter(name=Sava, published=true)
```

Пока в коде умолчание `published = true`, запись `{"name":"Sava"}` означает «опубликована». Если разработчик изменит умолчание на `false`, **все ранее сохранённые записи без этого поля молча станут черновиками**, и собака исчезнет с сайта. Запись всех полей явно (`encodeDefaults`) делает сохранённые данные самодостаточными: они больше не зависят от умолчаний в коде.

### Правила развития формата

| Изменение | Безопасно? | Как |
|---|---|---|
| Добавить поле | да, если есть значение по умолчанию | `val tags: List<String> = emptyList()` |
| Удалить поле | да, при `ignoreUnknownKeys` | старые записи сохраняют лишний ключ, пока их не пересохранят |
| Переименовать поле | **нет** | добавить новое, перенести данные, потом удалить старое |
| Изменить тип | **нет** | то же: новое поле рядом |
| Изменить смысл значения | **нет**, и компилятор не поможет | новое поле или явная миграция |

Проект следует «только добавлять». Это закреплено в `docs/decisions.md`: «A new field in the model therefore needs no migration». Тот же принцип в разделах, которые собирает админка: ключи полей (`f3`) и вариантов выбора создаются один раз и **никогда не переиспользуются**, чтобы значения удалённого поля не «вернулись» под новым полем с тем же ключом (счётчик `nextKeyNumber` в `Section` только растёт).

## Документы в таблицах

Как проект хранит кошку в базе? Не раскладывает по десяти таблицам, а кладёт целиком, как JSON-текст, в одну строку:

```sql
CREATE TABLE IF NOT EXISTS cats (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    data TEXT NOT NULL,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL
)
```

Колонка `data` содержит тот же JSON, что и файл `data/cats.json`. Это осознанный компромисс.

| | Документ в таблице (проект) | Нормализованная схема |
|---|---|---|
| Добавить поле | добавить в класс, миграция не нужна | `ALTER TABLE`, миграция, перенос данных |
| Запрос «все кошки на передержке» | загрузить все и отфильтровать в коде | `WHERE location = ...` |
| Целостность (внешние ключи, ограничения) | в коде | в базе |
| Работа с «язык + текст» | один объект `LocalizedText` внутри документа | отдельная таблица переводов и `JOIN` |
| Подходит для | десятки или сотни записей, читаются целиком | тысячи и больше, сложные выборки |

Приюту хватает десятков записей, и они всегда читаются и записываются целиком. Выигрыш от «никаких миграций» перевешивает потерю запросов по полям. Когда придёт время участников и визитов (персональные данные, связи), `docs/decisions.md` прямо говорит, что их нужно хранить отдельно и, вероятно, в нормальных таблицах.

:::note Почему TEXT, а не jsonb
PostgreSQL умеет `jsonb`, и по нему можно запрашивать. Но тесты проекта идут на H2 в режиме PostgreSQL, а там `jsonb` нет. Комментарий в коде: «a `text` column, not `jsonb`, so the same SQL runs on H2 in the tests». Полей, по которым ищут, нет, и `jsonb` ничего бы не дал.
:::

### id: колонка главнее документа

В документе тоже есть поле `id`, но это копия. При чтении проект берёт идентификатор из колонки:

```kotlin
add(withId(documentJson.decodeFromString(serializer, rows.getString(2)), rows.getInt(1)))
```

Источник истины должен быть один. Если бы настоящими считались оба, рано или поздно они разошлись бы.

## JDBC: безопасные запросы и транзакции

```kotlin
dataSource.connection.use { connection ->
    connection.prepareStatement("DELETE FROM cats WHERE id = ?").use { statement ->
        statement.setInt(1, id)
        statement.executeUpdate() > 0
    }
}
```

- `?` — **параметр запроса**. Значение передаётся отдельно (`setInt`, `setString`) и никогда не склеивается с текстом SQL. Это защита от SQL-инъекции: даже если в имени кошки окажется `'; DROP TABLE cats; --`, оно будет значением, а не командой.
- `use` закрывает соединение и запрос при любом исходе.
- `executeUpdate()` возвращает число изменённых строк. Проект использует его, чтобы узнать, было ли что удалять (`> 0`) или обновлять (`updated == 0` → `NoSuchElementException`).

:::warn Откуда в проекте `$table` внутри SQL
В `PgDocuments` имя таблицы подставляется в запрос обычной интерполяцией: `"SELECT id, data FROM $table ORDER BY id"`. Параметром `?` имя таблицы подставить нельзя, и это допустимо только потому, что `table` приходит из констант в коде (`"cats"`, `"dogs"`), а не из ввода пользователя. Правило: интерполяция в SQL допустима только для значений, которые целиком определены кодом. Всё, что пришло извне, идёт через `?`.
:::

### Транзакция: всё или ничего

Сохранение новой записи состоит из двух шагов: вставить строку (получить `id`) и записать этот `id` внутрь документа. Если упадёт второй, в базе останется документ с неверным `id`. Поэтому оба шага в одной транзакции (вспомните `inTransaction` из урока про [лямбды](lesson:k4-lambdas-dsl)):

```kotlin
val saved = dataSource.inTransaction { connection ->
    val id = idOf(item)
    if (id == 0) {
        val newId = ... INSERT ... generatedKeys ...
        val withRealId = withId(item, newId)
        ... UPDATE $table SET data = ? WHERE id = ? ...
        withRealId
    } else {
        ... UPDATE ...
    }
}
invalidate()
```

Запись с `id == 0` считается новой: ещё одно соглашение, на которое опираются репозитории («A cat with id 0 is new: the database gives it the real id»).

:::idea Подумайте
Вставка и тут же обновление выглядят неуклюже. Можно ли обойтись одной операцией? (Например, не хранить `id` внутри документа вовсе, как делают многие системы.) Что тогда придётся изменить в моделях и в файловом режиме, где `id` читается прямо из JSON?
:::

### Пул соединений и «спящая» база

Открывать соединение к базе дорого, поэтому используется пул. Настройки в `createDataSource` ([Database.kt](repo:src/main/kotlin/org/proanima/shelter/repository/Database.kt)) описывают конкретную среду:

```kotlin
maximumPoolSize = 3
minimumIdle = 0
idleTimeout = 60_000
maxLifetime = 240_000
connectionTimeout = 10_000
initializationFailTimeout = 30_000
```

Комментарий в коде объясняет каждую цифру: бесплатная база Neon **засыпает через пять минут простоя** и разрывает соединения, поэтому пул не держит простаивающих соединений (`minimumIdle = 0`) и обновляет их раньше пяти минут (`maxLifetime = 240_000` мс). Пробуждающейся базе нужно несколько секунд, отсюда `connectionTimeout = 10_000`. Никаких «поддерживающих» запросов: они бы не давали базе спать и тратили бесплатные часы.

Это пример настройки, выведенной из свойств **конкретной** платформы, а не из «рекомендуемых» значений.

## Кэш: быстрее, но не неправда

Каждая страница читает список кошек. Без кэша каждый просмотр означал бы запрос в базу, которая может спать. Проект кэширует список в памяти на 30 секунд, сбрасывает кэш при записи и, если база недоступна, отдаёт старую копию. Реализуем эту логику сами.

::::live Кэш с поколением и старой копией
Мы напишем `CachedList` — упрощённую версию `PgDocuments.findAll` без базы данных, чтобы запустить её в браузере.

:::step Шаг 1. Без кэша
Каждый вызов идёт в «базу».

```kotlin
fun findAll(): List<T> = load()
```

Страница сайта делает несколько обращений, база спит или отвечает секунды, посетитель ждёт.
:::

:::step Шаг 2. Кэш на время
Запоминаем результат и время загрузки; пока прошло меньше TTL, отдаём запомненное.

```kotlin
private class Snapshot<T>(val loadedAt: Long, val items: List<T>)
@Volatile private var snapshot: Snapshot<T>? = null

fun findAll(): List<T> {
    val cached = snapshot
    val time = now()
    if (cached != null && time - cached.loadedAt < ttlMillis) return cached.items
    return load().also { snapshot = Snapshot(time, it) }
}
```

Время берём через функцию `now`, а не напрямую из системы: так тест может двигать часы руками.
:::

:::step Шаг 3. Сброс при записи и поколение
После сохранения кэш должен сброситься. А ещё нужно не дать «медленному» чтению положить в кэш устаревшее (мы разбирали эту гонку в уроке про [конкурентность](lesson:k5-errors-concurrency)).

```kotlin
@Volatile private var generation = 0L

fun invalidate() {
    generation++
    snapshot = null
}

// in findAll:
val startedAt = generation
load().also { items -> if (generation == startedAt) snapshot = Snapshot(time, items) }
```
:::

:::step Шаг 4. Старая копия при отказе
Если база недоступна и у нас есть **любая** копия, отдаём её: устаревший список лучше, чем страница с ошибкой.

```kotlin
return try { load()... } catch (e: IllegalStateException) {
    if (cached == null) throw e      // nothing to fall back to
    cached.items
}
```

Если копии нет (первый запуск), исключение пробрасывается: честный отказ лучше выдуманных данных.
:::

:::step Шаг 5. Собираем и проверяем
```run
class CachedList<T>(
    private val ttlMillis: Long,
    private val now: () -> Long,
    private val load: () -> List<T>
) {
    private class Snapshot<T>(val loadedAt: Long, val items: List<T>)

    @Volatile
    private var snapshot: Snapshot<T>? = null

    // Counts writes. A read that started before a write must not cache its (already stale) result.
    @Volatile
    private var generation = 0L

    fun findAll(): List<T> {
        val cached = snapshot
        val time = now()
        if (cached != null && time - cached.loadedAt < ttlMillis) return cached.items
        val startedAt = generation
        return try {
            load().also { items ->
                if (generation == startedAt) snapshot = Snapshot(time, items)
            }
        } catch (e: IllegalStateException) {
            if (cached == null) throw e
            println("could not read (${e.message}); serving the old copy")
            cached.items
        }
    }

    fun invalidate() {
        generation++
        snapshot = null
    }
}

fun main() {
    var clock = 0L
    var database = listOf("Felix")
    var down = false
    var reads = 0
    val cache = CachedList(ttlMillis = 30_000, now = { clock }) {
        reads++
        if (down) error("database is asleep")
        database
    }

    println(cache.findAll())
    println("reads=$reads")
    database = listOf("Felix", "Mila")
    println(cache.findAll())
    cache.invalidate()
    println(cache.findAll())
    println("reads=$reads")
    clock = 31_000
    down = true
    println(cache.findAll())
}
```

```output
[Felix]
reads=1
[Felix]
[Felix, Mila]
reads=2
could not read (database is asleep); serving the old copy
[Felix, Mila]
```

Прочитайте вывод построчно: после первого чтения кэш хранит `[Felix]`; изменение «базы» не видно, пока кэш не сброшен или не истёк; `invalidate()` (запись) заставляет прочитать заново; по истечении 30 секунд база «упала», и сайт отдал последнюю копию.
:::

:::step Шаг 6. Что не так в этой картине
Честно оценим результат.

- **Свежесть.** Изменение, сделанное другим экземпляром приложения, до 30 секунд не видно. Для сайта с одним экземпляром это не важно; при нескольких экземплярах кэш рассинхронизируется.
- **Дублирование.** Та же логика в проекте написана **трижды** (`PgDocuments`, `PgSiteContentRepository`, `PgMenuRepository`) почти слово в слово. Это хороший кандидат на рефакторинг: общий `CachedValue<T>`. Именно на нём мы потренируемся в уроке про [рефакторинг](lesson:a4-refactoring).
:::

## Первый запуск: засеять базу один раз

Пустая база на первом запуске должна получить стартовые данные из `data/`. В `seedIfNeeded` ([Seeder.kt](repo:src/main/kotlin/org/proanima/shelter/repository/Seeder.kt)) есть тонкость: засевается не «если таблицы пусты», а «если нет **отметки** о засеве» в таблице `app_meta`. Отметка записывается в той же транзакции, что и данные.

Почему не проверять «пусто ли»? Если приют удалит последнюю собаку, таблица пуста, и после перезапуска образцы бы «воскресли». А «отметка в той же транзакции» даёт два свойства: засев происходит **ровно один раз** и **целиком** (при сбое на полпути в базе нет ничего, и следующий запуск повторит попытку). Это называется идемпотентной инициализацией.

::::task Найдите уязвимость
Волонтёр ищет кошку по имени. Что здесь не так и как исправить?

```kotlin
fun findByName(connection: java.sql.Connection, name: String): List<String> {
    val result = mutableListOf<String>()
    connection.createStatement().use { statement ->
        statement.executeQuery("SELECT data FROM cats WHERE data LIKE '%$name%'").use { rows ->
            while (rows.next()) result += rows.getString(1)
        }
    }
    return result
}
```

:::solution
Это **SQL-инъекция**: значение `name` попадает в текст запроса. Ввод `%' OR '1'='1` изменит смысл запроса, а ввод со специальными символами (`'`) просто сломает его.

Исправление: параметр.

```kotlin
connection.prepareStatement("SELECT data FROM cats WHERE data LIKE ?").use { statement ->
    statement.setString(1, "%$name%")
    statement.executeQuery().use { rows ->
        while (rows.next()) result += rows.getString(1)
    }
}
```

Символы `%` и `_` внутри самого `name` всё ещё работают как шаблон `LIKE`. Если нужен буквальный поиск, их надо экранировать. Заметьте, что в проекте такого поиска нет вообще: список кошек читается целиком и фильтруется в коде, и это одна из причин, по которым документная схема там уместна.
:::

::::task Документ или таблицы?
Через полгода команда хочет хранить **участников визитов** с их контактами и историей. Сравните два варианта хранения (JSON-документ в одной таблице против таблиц `visits`, `participants`, `visit_participants`) и выберите. Напишите 4–5 предложений с аргументами.

:::hint
Подумайте: нужны ли выборки «в каких визитах участвовал человек X»? Что с персональными данными: удаление по просьбе, ограничение доступа? Сколько записей будет через год?
:::

:::solution
Разумный ответ: **таблицы**. Аргументы:

1. Нужны запросы по связям («все визиты человека», «кто едет в субботу»): в документах пришлось бы грузить всё и перебирать в коде, а с ростом это дорого.
2. Это **персональные данные**: удаление одного человека (по его просьбе) в нормализованной схеме — один `DELETE`, а в документах — переписывание каждого визита, где он упомянут. В `docs/decisions.md` записано: «Participants should be stored separately from visits to make future migration to relational tables easier».
3. Целостность: внешние ключи не дают «осиротить» участие в несуществующем визите.
4. Каталог кошек остаётся документами: он маленький, читается целиком, часто меняется по форме.

Вывод: выбор схемы определяется тем, как данные **запрашиваются и защищаются**, а не модой. Разные части одного приложения могут жить в разных схемах.
:::

- [ ] Отключает проверку типов.

Q: Зачем `documentJson` включает `encodeDefaults = true`?
- [ ] Чтобы JSON был короче.
- [x] Чтобы в базе были записаны значения всех полей, и позднее изменение умолчания в коде не меняло смысл ранее сохранённых записей.
- [ ] Чтобы ускорить запись.
- [ ] Это требование PostgreSQL.
E: Без явной записи отсутствующее поле означает «возьми умолчание из кода». Изменив код, вы изменили бы старые данные.

- [x] Удалить поле (при `ignoreUnknownKeys`).
- [ ] Переименовать поле.
- [ ] Заменить тип поля с `String` на `Int`.

- [x] Значение передаётся отдельно от текста запроса и не может изменить его смысл.

- [ ] Это единственный способ получить `id` новой строки.

- [ ] PostgreSQL не умеет считать строки.

- [ ] Ради безопасности паролей.

## Итоги

- Формат хранения развивайте только добавлением полей с умолчаниями; явно записывайте значения (`encodeDefaults`).
- Документ в таблице — хороший выбор для небольших, целиком читаемых данных; для связей и персональных данных нужны таблицы.
- Все значения в SQL — через параметры, ресурсы — через `use`, группы шагов — через транзакцию.
- Кэш должен знать про сброс при записи, про гонку «старое чтение» и про отказ базы.
- Начальную загрузку защищайте отметкой, а не пустотой таблицы.
